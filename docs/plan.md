# План реализации jquiz (MVP)

Источник истины — `docs/spec.md` (далее «ТЗ»). Ссылки вида «ТЗ 8.1» — на его разделы.
Работа идёт строго по этапам; следующий этап начинается, когда у текущего выполнен
критерий готовности и `pytest -q` зелёный. В каждом этапе сначала пишутся тесты
с комментарием `# spec X.Y`, потом код. Решения по неясностям ТЗ — в разделе
«Принятые решения» (ссылки вида D7); тест на такое решение помечается `# decision D7`.

## Сквозные архитектурные решения

- **Раскладка.** Корень репозитория `jvm_tester_game/` играет роль папки `jquiz/` из ТЗ 14:
  в нём `pyproject.toml`, `src/jquiz/`, `tests/` (D1).
- **Константы.** Все числа из ТЗ (цены, коэффициенты весов, пороги, бонусы, лимиты) —
  в `src/jquiz/constants.py` (D2).
- **Реестр типов вопросов.** Каждый слой держит свой словарь `QuestionType -> обработчик`:
  `bank.VALIDATORS`, `checking.CHECKERS`, `ui.RENDERERS`, `session.FLOWS`. Отдельный тест
  проверяет, что каждый реестр покрывает все четыре типа. Цепочек `if type == ...` вне
  реестров нет (D3).
- **Время и случайность.** Чистые функции получают `now: datetime` (aware, локальное
  смещение) и `rng: random.Random`. Сессия получает `clock: Callable[[], datetime]` и `rng`.
  Только `cli` создаёт реальные часы (`datetime.now().astimezone()`) и `random.Random()`.
- **Файлы.** Читает и пишет только `storage`. `bank` валидирует уже разобранный JSON
  (список объектов) и возвращает `(questions, problems)`; ничего не печатает. Предупреждения
  выводит `ui` по вызову из `cli` (D4). Каталог данных (`~/.jquiz`) передаётся в `storage`
  параметром, поэтому в тестах используется `tmp_path`.
- **Статистика.** Отдельный чистый модуль `stats.py` (D5), правила те же, что для
  `selection` и др.: без ввода-вывода, файлов, часов и глобального random.
- **Ввод-вывод.** `ui` содержит чистые функции форматирования (перенос строк, цвета,
  ASCII-замены, отрисовка вопросов, итогов и статистики → строки), Protocol `IO`
  (`write(text)`, `read(prompt) -> str`) и `ConsoleIO` — единственное место с `print`/`input`.
  В тестах используется `FakeIO` (`tests/fakes.py`) с очередью ответов и списком
  выведенных строк.

## Этап 1. Каркас проекта и models.py

**Модули:** `pyproject.toml`, `src/jquiz/__init__.py`, `src/jquiz/__main__.py` (заглушка
с вызовом `cli.main`), `src/jquiz/constants.py`, `src/jquiz/models.py`, пустые модули
из ТЗ 14 и `stats.py`, `tests/conftest.py`, `tests/fakes.py` (`FakeIO`, фиксированные часы).

**Пункты ТЗ:** 2 (Python 3.10+, stdlib, console-script `jquiz`, `python -m jquiz`,
package data), 14 (структура); модели данных для 6.2–6.3, 7.3, 9.4, 10.

**Содержимое models.py:**
- `QuestionType` (enum: choice/short/output/open), `Outcome` (enum: correct, partial,
  wrong, dont_know, skipped, aborted).
- `Question` (frozen dataclass: id, topic, difficulty, type, question, options, code,
  answer, key_points, explanation).
- `QuestionProgress` (weight=1.0, correct/partial/wrong/dont_know/skipped=0, last_seen=None).
- `Daily` (date, answered, bonus_claimed), `Titles` (owned, active), `HistoryEntry`.
- `Progress` (version, coins, streak, best_streak, daily, questions, inventory, titles,
  history, `extra: dict` для неизвестных полей — ТЗ 10 «лишние поля сохраняются»).
- `ShopItem` (item_id, name, short_name для титулов — D29, price, kind, requires),
  `CustomReward` (item_id, name, price).

**Тесты (`tests/test_models.py`, `tests/test_package.py`):**
- значения по умолчанию `Progress()` и `QuestionProgress()` соответствуют ТЗ 8.1 и 10;
- `Outcome` и `QuestionType` содержат ровно значения из ТЗ 7.3 и 6.3;
- все модули пакета импортируются;
- константы из `constants.py` совпадают с числами ТЗ (цены 9.4, коэффициенты 8.1,
  пороги 8.2/8.4, бонусы 9.1, лимиты из 5 и 10).

**Критерий готовности:** `pip install -e ".[dev]"` проходит, `pytest -q` зелёный,
все модули из ТЗ 14 (+ `constants.py`, `stats.py`) существуют и импортируются.

## Этап 2. checking + bank

**Модули:** `checking.py`, `bank.py`.

**Пункты ТЗ:** 6.2, 6.3, 6.5 (логика валидации и дедупликации, сводка для validate),
7.2 (normalize_short, normalize_output, разбор ввода choice, перемешивание вариантов
с пересчётом индекса), 7.4 (применимость подсказок, результат 50/50 и «первой буквы»).

**Содержимое:**
- `checking`: `normalize_short`, `normalize_output`, `parse_choice_input(text, n) -> int | None`,
  `shuffle_options(options, correct, rng) -> (options, correct_index)`,
  `CHECKERS[type](question, answer, shown) -> bool`, `applicable_hint(type, n_options)`,
  `apply_5050(options, correct, rng)`, `first_letter_hint(question) -> (char, length)`.
- `bank`: `validate_bank(raw) -> BankResult(questions, problems, total)`, где проблема —
  (`id` или порядковый номер с 1, причина); `summarize(result)` — данные для
  «валидно X из Y, по темам: …, по типам: …». Не JSON-массив или пустой банк после
  валидации — исключение `BankError`.

**Тесты:**
- `tests/test_checking.py`: каждый шаг `normalize_short` по порядку; ` HashSet; ` ==
  `hashset`, `strip()` == `strip` (крит. 2); удаляются все завершающие `;`, но одна пара
  `()` (D11); `True` ≠ `true` для output (крит. 3); output обрезает только края;
  пустой ввод → «не ответ»; `parse_choice_input` для `abc`, `0`, `n+1`, ` 2 ` (крит. 4,
  логика); перемешивание сохраняет правильный вариант при фиксированном seed; 50/50
  оставляет правильный + один неверный в новом случайном порядке (D16), неприменима при
  <4 вариантах и для не-choice; «первая буква» только для short/output.
- `tests/test_bank.py`: валидный пример из ТЗ 6.2 проходит целиком; по одному тесту на
  каждое правило 6.3 (отсутствие каждого обязательного поля, неверный topic, difficulty
  вне 1–3, options <2/>6/дубликаты/пустые, индекс answer вне диапазона, пустой массив и
  пустые строки для short/output, `\n` в answer у output, answer не строка у open,
  key_points не массив строк, нет explanation у choice/short/output); `bool` вместо числа
  в `difficulty` и `answer` отклоняется (D9); поле «только для» другого типа (например,
  `options` у `short`, `code` у `choice`) делает вопрос некорректным (D8); `\r` в output
  не считается переводом строки (D10); дубликат `id` → остаётся первый валидный,
  остальные — проблема «дубликат» (D7, крит. 12); вопрос без `id` → порядковый номер;
  не массив → `BankError`; пусто после валидации → `BankError`; сводка по темам и типам.
- тест реестров: `CHECKERS` и `VALIDATORS` покрывают все `QuestionType`.

**Критерий готовности:** крит. 2, 3, 12 (логика) и часть 15 (нормализация, валидация)
зелёные; модули не используют `print`, `open`, `datetime.now`, глобальный `random`.

## Этап 3. selection (+ stats)

**Модули:** `selection.py`, `stats.py` (D5 — статистике нужны определения 8.4, поэтому
она идёт в этом же этапе).

**Пункты ТЗ:** 8.1, 8.2, 8.3, 8.4, 5 (фильтр темы, `--weak`, «доступно только K»),
11 (расчёт: итоги, по темам, слабые темы, топ-5 слабых вопросов), 10 (записи о
вопросах вне банка игнорируются).

**Содержимое:**
- `selection`: `new_weight(weight, outcome)`, `recency(last_seen, now)`,
  `score(qp, now)`, `topics(questions)`, `build_pool(questions, progress, topic, weak_only)`,
  `select(pool, n, progress, now, rng)` (взвешенный выбор без возвращения),
  `is_weak_question`, `is_weak_topic`.
- `stats`: `compute_stats(questions, progress) -> Stats` (итоги, % верных или `None` при
  0 ответах, по темам, топ-5 слабых).

**Тесты (`tests/test_selection.py`, `tests/test_stats.py`):**
- `new_weight` по таблице 8.1 для каждого исхода; нижняя граница 0.25 и верхняя 16;
  случайные последовательности исходов (seed) не выводят вес за 0.25–16 (крит. 5);
- `recency`: никогда не показан → 2.0; 23 ч → 0.5; ровно 1 сутки; 7 дней → 2.0;
  60 дней → 3.0; `last_seen` в будущем → 0.5 (D20);
- крит. 6: seed, 10 000 выборов одного вопроса из пула двух (веса 8 и 1, одинаковый
  recency) → отношение частот в 6–10;
- крит. 7: одинаковый вес, `last_seen` 12 ч и 7 дней назад → отношение ≈ 4 (диапазон 3–5);
- выбор без повторов, `min(N, размер пула)`, порядок = порядок выбора;
- пул: фильтр темы, `--weak` оставляет только `weight > 2.0`, пустой пул; темы берутся
  из текущего банка (D12);
- слабая тема: средний вес > 1.5, непоказанные считаются как 1.0; топ-5 по весу, при
  равенстве по `wrong + dont_know`, затем по `id`; процент верных; записи о вопросах
  вне банка не учитываются.

**Критерий готовности:** крит. 5, 6, 7 и расчётные части крит. 13, 14, 15 (recency,
веса, выбор) зелёные; функции принимают `now` и `rng` параметрами.

## Этап 5. storage

**Модули:** `storage.py`, `src/jquiz/data/questions.json` — минимальный валидный банк
(по одному-два вопроса каждого типа, D6).

**Пункты ТЗ:** 6.1 (выбор источника банка, `importlib.resources`), 6.5 (ошибка JSON →
`BankError`), 9.5 (чтение config.json, повреждённый файл игнорируется с предупреждением),
10 целиком.

**Содержимое:** `load_bank_raw(data_dir)`, `bank_source(data_dir)`,
`load_progress(data_dir, now) -> (Progress, notices)`, `save_progress(data_dir, progress)`
(атомарно: tmp в той же папке → flush → fsync → `os.replace`; обрезка истории до 200),
`backup_progress(data_dir, now)` (суффикс при коллизии, хранится не больше 5 бэкапов —
D23), `reset_progress(data_dir, now)`, `load_config(data_dir)`, сериализация и
десериализация `Progress` с сохранением лишних полей, `UnsupportedVersionError`.

**Тесты (`tests/test_storage.py`, на `tmp_path`):**
- банк: при наличии `questions.json` в каталоге берётся он, иначе встроенный; встроенный
  банк читается и проходит `validate_bank`;
- roundtrip `Progress` без потерь; отсутствующие поля → значения по умолчанию; лишние
  поля (в корне и в записи вопроса) сохраняются; записи о вопросах вне банка сохраняются;
- присутствующее поле неверного типа → повреждение (D21); вес вне 0.25–16 при загрузке
  обрезается до границ (D20);
- время пишется в ISO 8601 с локальным смещением;
- история обрезается до 200 последних;
- атомарность: `os.replace` подменён на падающий → старый файл цел и валиден, временный
  файл не остаётся (крит. 10);
- повреждённый JSON или неверная структура → файл переименован в
  `progress.json.bak.YYYYMMDD-HHMMSS`, возвращён чистый прогресс и уведомление (крит. 11);
- два бэкапа в одну секунду → второй с суффиксом `-1`; при шестом бэкапе удаляется
  самый старый (D23);
- `version` больше поддерживаемой → исключение, файл не изменён;
- reset сохраняет копию и пишет чистый прогресс; reset без файла — просто чистый прогресс;
- config.json: отсутствует → нет наград; повреждён → предупреждение, игнор;
- каталог `~/.jquiz` создаётся при первой записи;
- сохранение → загрузка сохраняет монетки, стрик и `daily` (крит. 8, «переживают
  перезапуск»).

**Критерий готовности:** крит. 10 и 11 (хранение) и сохранение между запусками из
крит. 8 зелёные; файлы трогает только `storage`.

## Этап 7. session

**Модули:** `session.py`.

**Пункты ТЗ:** 7.1, 7.2 (ход по типам, повторные запросы), 7.3 (исходы и вывод после
них), 7.4 (подсказки в вопросе), 8.3 п.4 (порядок, без повторов, состав фиксирован),
10 (сохранение после каждого исхода, кроме `aborted`), 12 (итог, в т.ч. при досрочном
выходе).

**Содержимое:** `run_session(questions, progress, io, style, clock, rng, save) ->
SessionSummary`; `FLOWS[type]` — пошаговый сценарий вопроса; `save` — колбэк
(в проде `storage.save_progress`), чтобы session не знал о файлах.

**Тесты (`tests/test_session.py`, с `FakeIO`):**
- сессия по банку со всеми четырьмя типами: отображение и проверка каждого
  (крит. 1, уровень сессии);
- choice: `abc`, `0`, `5` при 4 вариантах → повторный запрос, прогресс не меняется,
  `save` не вызван до валидного ответа (крит. 4);
- short/output: пустой ввод → повтор;
- `:h` без расходника, неприменимая подсказка, повторная подсказка → причина, расходник
  не списан, повтор (крит. 9); 50/50 перенумеровывает 1 и 2 и принимает ответ в новой
  нумерации; «первая буква» показывает символ и длину;
- `:s` без расходника → причина; с расходником → `skipped`, расходник списан;
- `:n` → `dont_know`; `:n` в open → причина;
- open: до эталона доступны только `:s`/`:q`, на самооценке только `:q`, ввод кроме
  1/2/3 → повтор; 1/2/3 → correct/partial/dont_know;
- `:q` → `aborted`: вопрос нигде не учтён, `save` не вызывается, итог выведен (D14);
  подсказка, использованная до `:q`, возвращается в инвентарь (D15);
- EOF и Ctrl+C при вводе обрабатываются как `:q` (D19);
- `save` вызывается после каждого не-`aborted` исхода с актуальным прогрессом;
  `FakeIO`, бросающий исключение после K ответов, — сохранено ровно K исходов
  (крит. 10, уровень сессии);
- две сессии подряд с общим хранилищем на `tmp_path`: стрик и монетки переносятся,
  смена даты в `clock` между сессиями сбрасывает дневной счётчик (крит. 8);
- итог: «лучший стрик в сессии» = максимум сохраняемого стрика, достигнутый за эту
  сессию (стрик продолжается с прошлого запуска, D17); счётчики, монетки, темы с
  ошибками, разбор ошибок.

**Критерий готовности:** крит. 1, 4, 9 и 10 на уровне сессии зелёные; `session` не
использует `print`/`input`/`open`/`datetime.now`.

## Принятые решения по неясностям ТЗ

**Архитектура и структура**

- **D1.** Корень репозитория `jvm_tester_game/` = папка `jquiz/` из ТЗ 14.
- **D2.** Константы — в новом модуле `constants.py`.
- **D3.** Реестры по слоям (`VALIDATORS`, `CHECKERS`, `RENDERERS`, `FLOWS`) + тест полноты;
  общий реестр не делаем, иначе `models` зависел бы от `ui`.
- **D4.** `storage` читает и парсит JSON банка, `bank` только валидирует список и
  возвращает проблемы, печатает `ui` по вызову из `cli`.
- **D5.** Статистика — новый чистый модуль `stats.py` (этап 3).
- **D6.** Встроенный банк в MVP — минимальный валидный набор (этап 5). Требования ТЗ 6.4
  (80+ вопросов, 10 тем, ≥6 на тему, ≥10 на тип, ручная проверка ответов) этим планом
  не закрываются — наполнение банка остаётся отдельной задачей вне 8 этапов.

**Банк и проверка**

- **D7.** Дубликаты `id` ищутся среди прошедших валидацию: остаётся первый валидный,
  остальные — проблема «дубликат id».
- **D8.** Поле, разрешённое только другому типу (`options` не у choice, `code` не у
  output, `key_points` не у open), делает вопрос некорректным.
- **D9.** `bool` вместо целого (`difficulty`, `answer` у choice) явно отклоняется.
- **D10.** В answer у output запрещён только `\n`.
- **D11.** `normalize_short`: удаляются все завершающие `;`, затем одна завершающая пара `()`.
- **D12.** Темы для `-t` берутся из текущего банка, а не из списка 6.4: так банк и его
  темы можно будет расширять в будущем без изменения кода. Само расширение банка в MVP
  не делается.

**Сессия и экономика**

- **D13.** Дневной бонус: при `answered >= 10 and not bonus_claimed`, где `answered`
  считает исходы correct/partial/wrong/dont_know (как дневной счётчик 9.2).
- **D14.** При `aborted` файл не записывается (всё уже сохранено после прошлых исходов).
- **D15.** Подсказка, использованная в вопросе, который закончился `aborted`, возвращается
  в инвентарь.
- **D16.** После 50/50 два оставшихся варианта перемешиваются заново.
- **D17.** Стрик сохраняется между запусками (ТЗ 9.2). «Лучший стрик в сессии» — максимум
  этого стрика, достигнутый за сессию, с учётом продолжения с прошлого запуска.
- **D18.** После `dont_know` выводится «✘ Неверно» красным. Метки open: «✔ Знал»,
  «◐ Частично», «✘ Не знал».
- **D19.** EOF и Ctrl+C во время сессии = `:q`: итог выводится, код 0.
- **D20.** `last_seen` в будущем → recency 0.5 (меньше суток); вес вне 0.25–16 в файле
  при загрузке обрезается до границ.

**Хранение**

- **D21.** Корень не объект или присутствующее поле неверного типа → файл повреждён
  (бэкап + чистый прогресс). Отсутствующее поле → значение по умолчанию.
- **D22.** В `history` пишутся только покупки.
- **D23.** При коллизии имени бэкапа добавляется суффикс `-1`, `-2`… Хранится не больше
  5 последних бэкапов, более старые удаляются. Это дополнение к ТЗ 10 по решению
  пользователя.
- **D24.** `reward-N` нумеруются по валидным записям (если исправить некорректную запись,
  номера последующих наград сдвинутся).

**CLI и вывод**

- **D25.** Коды выхода: отказ по бизнес-правилу (нет денег, условие, титул уже куплен,
  титул не куплен) → 1; неизвестный `item_id`/`title_id` → 2; `title off` без активного
  титула → сообщение, 0.
- **D26.** Глобальные флаги (`--no-color`, `--ascii`) принимаются и до, и после подкоманды.
- **D27.** Отчёт `validate` — в stdout, предупреждения при загрузке банка — в stderr.
- **D28.** Обрезка до 40/60 символов с `…` (в ASCII-режиме `...`); при 0 ответах вместо
  процента «—».
- **D29.** У титулов в каталоге хранится отдельное короткое имя для шапки («Middle»).
